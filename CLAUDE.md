# CLAUDE.md: Agent Platform

Coding-agent guide for this repository. Read this before writing any code. For lookup protocol, layer rules, testing/error conventions, and extension guidance, the primary authority is `AGENTS.md`, this file only adds current-state context and near-term priorities on top of it.

- **`src/agent_platform/README.md`**, layer map and known issues

## Current state (as of 2026-07-29, `core/tracing.py` was split into vendor-agnostic OTel plumbing (`tracing.py`: `TracingConfig`/`configure_tracing`/`traced_span`/`mark_span_error`) and a GenAI semantic-convention layer on top of it (new `core/genai_tracing.py`: `GenAIAttributes`/`traced_operation_span`/`record_token_usage`); `traced_span`/`traced_operation_span` also switched from `**attributes: Any` to an explicit `attributes: Mapping[str, Any] | None` parameter, since GenAI's dotted attribute keys were never usable as real kwargs, and tool-error span tagging in `agents/tools/registry.py` now reuses the new shared `mark_span_error()` instead of a hand-rolled duplicate. Mapper functions were also split out of provider files across `integrations/`: every provider (or shared base file) with real vendor-type-to-core-schema conversion logic now keeps that logic in a sibling `mappers.py` instead of inline in `provider.py`, see `integrations/README.md`'s "Provider and mapper files" section)

The platform is **structurally complete** at the integration, component, pipeline, agent, and evals layers. The remaining gap is `workflows/`, still an empty scaffold; `api/` has a real FastAPI entrypoint (`api/app.py`) wiring one `ConversationAgent` via `config/container.py::build_agent()`, driven by `config/settings.py::Settings`. That agent already carries `GenerateImageTool`/`TranscribeTool`, not chat only: `Settings.default_llm_model`/`default_image_model`/`default_audio_model` are `"<provider>:<model>"` strings (`core/config.py::parse_model_string`) resolved against each domain's `PROVIDER_ALIASES` map (`integrations/<domain>/__init__.py`) by `build_provider`/`build_provider_from_model_string`.

### What is solid

- **Core**, interfaces, schemas, error hierarchy, credentials: complete and stable, including `core/interfaces/classification/base.py` (`BaseClassificationProvider` ABC, added alongside the other domain ABCs)
- **Integrations**, 14 domains with providers: complete (see `integrations/README.md` for the full table). Every provider (or shared base file, e.g. `chunking/langchain_base.py`) that has more than a couple of free-standing vendor-type-to-core-schema conversion functions keeps them in a sibling `mappers.py` rather than inline in `provider.py` (22 per-provider `mappers.py` files across `llm`, `vector_store`, `ocr`, `image_generation`, `speech_to_text`, `clustering`, plus `chunking/mappers.py`); providers with only thin inline conversions (`embeddings`, `reranking`'s network providers, `translation`, `vad`, etc.) were left as-is. This is in addition to the existing domain-level shared conversion modules `ocr/utils.py`, `speech_to_text/utils.py`, and `reranking/scoring.py`. Also including `classification/transformers` (zero-shot via `pipeline("zero-shot-classification")`, consuming the `classification-transformers` extra) and the new `moderation` domain (`openai` via `omni-moderation-latest` + a local offline keyword-rule fallback, sharing `_base.py::NativeModerationProvider` for the network-bound provider, same dual-client shape as `reranking/_base.py::NativeReranker`). Provider SDKs install via per-provider `pyproject.toml` extras (e.g. `llm-openai`, `vector-store-chroma`), not a monolithic dependency list. The `llm`, `embeddings`, `vector_store`, and `reranking` domains (21 providers total, including the new `llm/google`/`embeddings/google` Gemini provider) each call their vendor's native SDK or REST endpoint directly now, no LangChain intermediate; each domain's shared `langchain_base.py` has been deleted along with the `langchain-*` deps it pulled in. `chunking` is the only domain that still has a shared `langchain_base.py`, wrapping `langchain-text-splitters` directly (a genuinely useful splitting library, not a thin pass-through). `llm`, `embeddings`, `reranking`, `translation`, and `moderation` each have a native, non-LangChain shared base instead: `integrations/<domain>/_base.py` (`NativeLLMProvider`/`NativeEmbeddingProvider`/`NativeReranker`/`NativeTranslator`/`NativeModerationProvider`) factors the tracing/retry/token-usage or request/response plumbing that's identical across that domain's providers, so each provider file holds only its vendor-specific client construction and mapping logic; this never crosses domain boundaries (e.g. `llm/openai` and `embeddings/openai` still duplicate their small client-kwargs snippet on purpose, since integrations must stay self-contained per `integrations/README.md`). `reranking`'s local providers (`huggingface`, `flashrank`) and `moderation`'s `local` provider don't use their domain's native base, same reasoning as other local/offline compute being exempt from the retry wrapper. `speech_to_text` has a narrower shared `_base.py::buffered_stream()` (a free async generator, not a provider base class) factoring the client-side windowing loop shared by `whisperx`/`faster_whisper`/`openai`'s `stream()`; `deepgram` is exempt since its streaming is a native socket protocol, not client-side batching. `ocr` and `image_generation` were evaluated for the same pattern and deliberately left without a shared base: vendor-specific response shapes (e.g. OCR bounding boxes) mean a template would add abstraction without removing real duplication. Every provider method that does real work now ships in a sync/async pair (`rerank`/`arerank`, `translate`/`atranslate`, `generate`/`agenerate`, `embed_document`/`aembed_document`, `detect`/`adetect`, `moderate`/`amoderate`), matching how modern provider SDKs ship distinct sync/async clients; streaming methods stay async-only, and `llm`'s `stream()` now also accepts a `tools` param, yielding `ToolCallDelta` fragments on `StreamChunk` (real per-fragment deltas from OpenAI/Anthropic, one whole delta per call from Mistral/Ollama/HuggingFace/Gemini). `llm/openai` and `llm/anthropic` additionally implement `core/interfaces/llm/batch.py::BaseBatchLLMProvider` (`submit_batch`/`get_batch_status`/`fetch_batch_results`), a separate mixin ABC rather than part of `BaseLLMProvider` since Mistral/Ollama/HuggingFace/Gemini have no first-class batch API to implement it against. `vector_store/qdrant` implements `add_hybrid`/`search_hybrid` (dense+sparse hybrid search, fused server-side via Qdrant's RRF `FusionQuery`), paired with a new local `embeddings/bm25` provider (`core/interfaces/embeddings/sparse.py::BaseSparseEmbeddingProvider`, a separate ABC from `BaseEmbeddingProvider` since it returns a `SparseVector` not a dense one) that produces raw term-frequency sparse vectors via feature hashing, no corpus-fit step needed since Qdrant's server-side `Modifier.IDF` handles the weighting; Pinecone hybrid support is an explicit non-goal since Pinecone expects a client-side-fitted sparse encoder, a different stateful shape. `chunking`, `clustering`, `classification`, `loader`, and `embeddings/bm25` (purely local/offline compute, no vendor sync/async split to mirror) are not held to that pairing
- **Components**, `Embedder`, `Chunker`, `Loader`, `Reranker`, `Generator`, `VectorSearch`, `SimilarityScorer`, `EmbeddingClassifier`, `LLMClassifier`: complete
- **Pipelines**, `pipelines/rag/ingest.py` (loader → chunk → embed via `Embedder` → store, `BaseVectorStore.add()` takes precomputed vectors directly), `pipelines/rag/query.py` (embed query → search → rerank → generate), `pipelines/speech_translation.py` (`SpeechTranslationPipeline.run()`/`.stream()`, audio → STT → translate with streaming support): complete
- **Agents**, `Agent`, `AgentExecutor`, `ConversationAgent`, `ToolRegistry`, `TranscribeTool`, `SearchTool`, `OCRTool`, `TranslateTool`, `ClassifyTool`, `GenerateImageTool`, `SummarizeTool`: complete
- **Evals**, `evals/` package (`EvalCase`/`EvalDataset`/`EvalRunner`/`Scorer`/`EvalReport`, `agent-platform-eval` CLI, golden `ConversationAgent`/`AgentExecutor` tool-selection dataset), Phase 1 of the agents-layer roadmap: complete, see `evals/README.md`
- **Tooling**, mypy and import-linter are wired into CI (`.github/workflows/ci.yml`) alongside ruff and pytest; the layered-architecture and core-isolation rules in AGENTS.md §6 are enforced by `lint-imports`, not just convention; an optional `evals` CI job runs the golden dataset against a real provider when `OPENAI_API_KEY` is set (`continue-on-error: true` until a real-run baseline validates the threshold)
- **Test suite**, `tests/` (structural + coverage-gate pass done): `pyproject.toml [tool.pytest.ini_options] addopts` enforces `--cov-fail-under=90` locally and in CI (config lives in `pyproject.toml [tool.coverage.*]`, no `.coveragerc`). Mocking goes through the `pytest-mock` `mocker` fixture, not raw `unittest.mock.patch`; every test is auto-marked `unit` via a `pytest_collection_modifyitems` hook in `tests/conftest.py` unless explicitly marked `integration` (currently 0 tests are, the suite is fully mocked); shared helpers live in `tests/helpers/`. See AGENTS.md §3 for the full convention
